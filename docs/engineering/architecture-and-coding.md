# 架构与编码规范

本规范适配自 `design-first-development` 工程规范。领域语义由项目 owning 文档维护，不能把通用规则当作新增功能的理由。

## 对象与状态归属

非简单实现前，明确每个对象的唯一职责、状态 owner、不变量、协作者、生命周期与线程归属。状态与保护该状态的规则位于同一 owner；入口类以接收、委派、组装和生命周期协调为主。

Core 不依赖 Spring、网络、持久化客户端或观测框架。外部技术通过已确认的适配边界进入；不要创建无语义 Context/Dependencies 来隐藏职责膨胀。

公共 API 保持最小，错误使用明确类型或码。公共配置、ID 编码或失败语义变化先更新 owning 文档及 ADR，不因实现方便默默改变保证。

## 生命周期与资源

每个资源、队列、定时器、缓冲和可变集合必须有唯一 owner、容量、失败及关闭策略。接受、完成、超时、取消和结果未知分别定义。重试必须有边界；不引入无人管理线程、无界队列或无界等待。

发号热路径仅访问本地状态，外部节点分配/占用维护归适配层。不能通过超时、关闭或降级绕过唯一性前提；静态配置不能冒充有效租约。

指标与诊断通过内聚、只读、有界的观察边界接入，不污染核心业务状态。禁止为测试或性能降低正确性断言。

## Java 工程约定

生产字节码目标为 Java 9；只使用公开 API，不使用 Lombok、Unsafe 或 JDK 内部 API。API/Core 不依赖反射。不提前引入 Multi-Release JAR 或 JPMS 描述符。

遵循[模块边界](../04-Module-Boundaries.md)，具体状态与线程归属见[系统架构](../02-System-Architecture.md)；避免含糊的工具类命名和一个方法一个接口的机械拆分。

## 完成前复审

检查状态 owner 是否唯一，是否扩大入口职责，依赖是否逆向，生命周期与失败是否明确，观察是否影响业务，契约是否重复，以及设计、实现、测试、授权范围是否一致。每个 PASS 必须有对应实际证据。

触发重新建模的具体条件由[模式策略](design-pattern-policy.md)维护；当前对象及线程归属见系统架构。
